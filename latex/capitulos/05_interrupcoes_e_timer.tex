\section{Descrição}
%-------------------------------------------------------------------------------
% Descreva em alto nível o que este módulo faz e qual problema ele resolve
% dentro do sistema operacional.
%
O módulo de tratador de interrupções de um Sistema Operacional (SO) é responsável por receber as interrupções geradas pelo \emph{hardware} ou pelo \emph{software} e executar a respectiva rotina de tratamento para o tipo de interrupção recebida.

As interrupções são sinais gerados pelo \emph{hardware} ou \emph{software} que indicam que algum evento precisa de atenção completa do processador para serem tratados corretamente. Essas interrupções podem ocorrer por meio de chamadas de sistema, instruções específicas, erros em tempo de execução, entre outras rotinas. Desse modo, o tratador de interupções é um módulo essencial do \emph{kernel} do SO, porque ele define as rotinas de tratamento para realizar cada uma das respostas apropriadas para os sinais de interrupção recebidos.

\section{Decisões de Arquitetura e Design}
%-------------------------------------------------------------------------------
% Justificar o porque de ter feito as coisas de uma certa maneira.
%
% Tópicos a cobrir:
% - Quais alternativas foram consideradas?
% - Por que a abordagem escolhida foi a melhor para este projeto?
% - Quais são as limitações ou trade-offs da abordagem escolhida?
%
Para a implementação do tratador de interrupções, foi utilizada uma abordagem similar ao SO Minix, que é a utilização de uma tabela de vetores de bits que endereça fisicamente na memória onde está localizado a rotina específica de tratamento de interrupção, onde cada entrada dessa tabela possui um tipo de interrupção endereçada pelo \emph{offset} de bits enviados.

Em termos mais simples, o sistema mantém um vetor de rotinas de tratamento, em que cada posição corresponde exatamente ao ID da interrupção que aquela rotina trata. Dessa forma, ao receber uma interrupção, o SO consegue fazer o processador pular exatamente para o código que trata aquela interrupção.

Essa abordagem foi escolhida para que o acesso à rotina de tratamento de interrupções possa ser feito com complexidade constante, aumentando a eficiência que o tratamento de interrupções ocorre e reduzindo o período em que o processador mantêm-se ocupado com a rotina de tratamento.

\section{Detalhes da Implementação}
%-------------------------------------------------------------------------------
% Descreva como a solução foi implementada, conectando o código
% à teoria.
%
% Tópicos a cobrir:
% - Principais estruturas de dados (structs) e suas funções.
% - Algoritmos chave utilizados.
% - Fluxo de execução das funções mais importantes.

Em um computador, o processador não se conecta diretamente a todos os dispositivos ao mesmo tempo. Em vez disso, existe um componente de \emph{hardware} intermediário chamado Controladora de Interrupções. Na arquitetura ARM, ele é conhecido como GIC (\emph{Generic Interrupt Controller}). O GIC funciona como um ``recepcionista'': ele recebe os sinais de interrupção de vários periféricos, organiza quem tem prioridade e envia um único aviso coordenado para a CPU.

Para que o Sistema Operacional consiga se comunicar com o GIC ele precisa ler e escrever em registradores de controle, que são mapeados em endereços especiais de memória pré-determinados pelo \emph{hardware} (neste caso, a placa \emph{virt} do QEMU). Essas definições de endereço, juntamente com os identificadores de cada dispositivo na placa (como o Timer, que é o ID 30), foram centralizadas no arquivo \texttt{include/vboard.h}:

\begin{lstlisting}[language=C]
// O GIC na arquitetura ARM é dividido em dois blocos principais:
// Distribuidor (GICD): Recebe os sinais do hardware e organiza a fila.
#define GICD_BASE 0x08000000

// Interface da CPU (GICC): É o canal direto entre o GIC e o processador,
// usado pela CPU para confirmar que começou a tratar ou que terminou.
#define GICC_BASE 0x08010000

// Interrupt Set: Registrador usado para ligar uma interrupção.
// São 128 bytes (1024 bits) de números de 32 bits.
#define GICD_ISENABLER ((volatile uint32_t *)(GICD_BASE + 0x100))

// Interrupt Clear: Registrador usado para desligar uma interrupção.
// São 128 bytes (1024 bits) de números de 32 bits.
#define GICD_ICENABLER ((volatile uint32_t *)(GICD_BASE + 0x180))

// Interrupt Configuration: Registrador para configurar o tipo de sinal
// esperado pelo controlador.
#define GICD_ICFGR     ((volatile uint32_t *)(GICD_BASE + 0xC00))

// O hardware do QEMU 'virt' fixa o Timer interno da CPU no ID 30.
#define TIMER_IRQ 30

// A controladora serial (UART0), por onde passam os dados do teclado.
#define UART0_IRQ 33
\end{lstlisting}

Seguindo a linha de pensamento abordada, foi utilizado um vetor com ponteiros de função para armazenar os \textit{handlers}. Assim, para registrar um tratador para interrupção de algum dispositivo, basta inserir um apontador para a rotina na posição correta do vetor.

Além disso, é utilizada uma \emph{struct} denominada \emph{Interrupts Sevice Routine} (isr) responsável por realizar o resgistro das funções que farão o tratamento de interrupções pelos dispositivos.

\begin{lstlisting}[language=C]
// Ponteiro para rotina.
typedef void (*isr_t)(void);

// Vetor de ponteiros para rotina.
static isr_t interrupt_handlers[MAX_INTERRUPTS] = {0};
\end{lstlisting}

Para isso, são utilizadas algumas funções que tem por objetivo a manipulação dos bits presentes nos registradores GIC (\emph{Generic Interrupt Controller}) da arquitetura ARM (arquitetura selecionada para a execução do projeto), que são registradores divididos por blocos lógicos responsáveis por gerenciar, priorizar e rotear interrupções. Para a etapa realizada neste projeto, os blocos mais utilizados para a configuração de interrupções no núcleo do sistema operacional são o bloco distribuidor \emph{Generic Interrupt Controller Distributor} (GICD) e o bloco de interface da CPU \emph{Generic Interrupt Controller CPU Interface} (GICC).

Esses blocos são manipulados pelas funções \emph{gic\textunderscore{}enable\textunderscore{}interrupt()}. Para o GIC gerenciar todos os 1024 dispositivos, ele armazena vetores com 32 registradores de 32 bits ($32 * 32 = 1024$), em que cada bit é referente ao dispositivo que tem ID igual a sua posição. Para encontrar o bit referente a um certo ID, basta fazer a divisão inteira para encontrar o registrador e o resto da divisão para encontrar o bit dentro dele.
\begin{lstlisting}[language=C]
void gic_enable_interrupt(uint32_t irq) {
  if (irq >= MAX_INTERRUPTS)
    return;

  // cada registrador tem 32 bits
  uint32_t reg_index = irq / 32;  // qual registrador
  uint32_t bit_offset = irq % 32; // qual bit do registrador

  GICD_ISENABLER[reg_index] |= (1 << bit_offset);
}
\end{lstlisting}
e \emph{gic\textunderscore{}disable\textunderscore{}interrupt()}, análogo ao \emph{gic\textunderscore{}enable\textunderscore{}interrupt()}, só que desativa a interrupção selecionada e modifica os registradores GICD\textunderscore{}ICENABLER para sinalizar que a interrupção está desativada;
\begin{lstlisting}[language=C]
void gic_disable_interrupt(uint32_t irq) {
  if (irq >= MAX_INTERRUPTS)
    return;

  uint32_t reg_index = irq / 32;
  uint32_t bit_offset = irq % 32;

  // No ICENABLER escrever 1 desliga a interrupcao
  GICD_ICENABLER[reg_index] = (1 << bit_offset);
}
\end{lstlisting}

Desse modo, o fluxo principal de execução funciona da seguinte forma: um gatilho de \emph{hardware} altera os bits de informação que são lidos pelo tratador como um tipo volatile uint32\_t (32 bits sem sinal), que indica ao compilador que o valor de bits pode ser mudado inesperadamente fora do controle ou da visibilidade da execução do tratador, e são levados aos registradores GIC;
\begin{lstlisting}[language=C]
// Registradores
#define GICD_CTLR (*(volatile uint32_t *)(GICD_BASE + 0x000))
#define GICC_CTLR (*(volatile uint32_t *)(GICC_BASE + 0x000))
#define GICC_PMR (*(volatile uint32_t *)(GICC_BASE + 0x004))
#define GICC_IAR (*(volatile uint32_t *)(GICC_BASE + 0x00C))
#define GICC_EOIR (*(volatile uint32_t *)(GICC_BASE + 0x010))
\end{lstlisting}

Para que o GIC comece a despachar os sinais para a CPU, é necessário inicializar seus blocos de controle através da função \texttt{init\_gic()}:

\begin{lstlisting}[language=C]
void init_gic(void) {
  GICD_CTLR = 1;   // Habilita o bloco Distribuidor (GICD)
  GICC_CTLR = 1;   // Habilita a Interface da CPU (GICC)
  GICC_PMR = 0xFF; // Priority Mask: aceita interrupcoes de qualquer prioridade
}
\end{lstlisting}

após isso, a informação é levada à tabela de vetores em linguagem de máquina, que desvia a execução do programa para ela;
\begin{lstlisting}[language=arm]
vector_table:			          // Offset | Interrupção | Modo de execução 
    b _start			          // 0x00   | Reset	      | supervisor
    b undefined_handler     // 0x04   | Undefined	  | undefined
    b svc_handler           // 0x08   | SVC  	      | supervisor
    b .                     // 0x0C   | Prefetch    | abort
    b data_abort_handler    // 0x10   | Data Abort  | abort 
    b .                     // 0x14   | Hyp Trap    | hypervisor
    b irq_handler           // 0x18   | IRQ         | interrupt
    b .                     // 0x1C   | FIQ         | fast interrupt
\end{lstlisting}

Contudo, para que a CPU saiba onde essa tabela está localizada, é necessário configurá-la antes de receber qualquer interrupção. Isso é feito pela função \texttt{setup\textunderscore{}core\textunderscore{}for\textunderscore{}irq} escrita em Assembly:

\begin{lstlisting}[language=arm]
setup_core_for_irq:
    ldr r0, =vector_table
    mcr p15, 0, r0, c12, c0, 0   // Grava a tabela no VBAR
    
    mrs r1, cpsr
    bic r0, r1, #0x1f
    orr r0, r0, #0xd2            // Entra no modo IRQ
    msr cpsr_c, r0
    
    ldr sp, =stack_top
    sub sp, sp, #8192            // Isola a pilha
    bic sp, sp, #7               // Alinhamento de 8 bytes
    msr cpsr_c, r1               // Volta ao modo anterior
    bx lr
\end{lstlisting}

Esse trecho realiza três tarefas fundamentais: primeiro, utiliza a instrução de hardware \texttt{mcr} (\textit{Move to Coprocessor from Register}) para acessar componentes internos da CPU. A combinação de parâmetros \texttt{(p15, 0, r0, c12, c0, 0)} serve como rota para localizar o registrador especial VBAR (\textit{Vector Base Address Register}) dentro do coprocessador de sistema (\texttt{p15}) e gravar nele o endereço de onde nossa vector\_table está na memória. Segundo, altera temporariamente o modo do processador para o modo IRQ (valor \texttt{0xd2}) apenas para inicializar o ponteiro de pilha (\texttt{sp}) recuando 8192 bytes. Isso garante que as interrupções tenham uma pilha isolada da pilha principal do \emph{kernel}, evitando corrupção de dados. Terceiro, o \texttt{bic sp, sp, \#7} garante o alinhamento obrigatório de 8 bytes da arquitetura ARM.

Com a CPU configurada, quando uma interrupção ocorre, a execução é desviada para a tabela, que por sua vez salta para a função \emph{irq\textunderscore{}handler}. Esta função ajusta o registrador de retorno da arquitetura e empilha todos os registradores na pilha isolada para salvar o contexto do processo interrompido:

\begin{lstlisting}[language=arm]
irq_handler:
    sub lr, lr, #4
    
    // Uma pseudo-instrucaoo que armazena os registradores de uso geral R0-R12 e o LR (Link Register)
    // e ao mesmo tempo atualiza o valor do stack pointer (sp) para o topo da pilha apos o armazenamento
    stmfd sp!, {r0-r12, lr}
    
    blx irq_dispatcher_c // Salta para a funcao em C
    
    // Uma pseudo-instrucao que restaura os registradores R0-R12 da pilha
    // e ao mesmo tempo copia o valor antigo de LR direto para o program counter (PC)
    ldmfd sp!, {r0-r12, pc}^
\end{lstlisting}

É crucial notar dois detalhes didáticos neste código em Assembly. A instrução \texttt{sub lr, lr, \#4} é obrigatória porque a CPU ARM executa instruções em \emph{pipeline}. Quando a interrupção congela a CPU, o registrador de ligação (\emph{Link Register} - \texttt{lr}) já está apontando para a instrução adiante. Subtrair 4 corrige esse atraso, garantindo que o SO retorne exatamente para o ponto em que parou. Além disso, o acento circunflexo (\texttt{\^}) no final da instrução \texttt{ldmfd} instrui o processador a não apenas restaurar os registradores gerais, mas também restaurar automaticamente o registrador de \emph{status} (CPSR), devolvendo a CPU ao modo de operação anterior à interrupção.

Uma vez que o tratador de interrupções (em C) está em execução, o registrador GICC\textunderscore{}IAR é lido para que o tratador saiba que interrupção o chamou e se essa interrupção possui uma rotina de tratamento configurada para ela. Caso possua, o tratador faz o desvio para a rotina específica armazenada no vetor de ponteiros de funções \emph{interrupt\textunderscore{}handlers} e salva o identificador da rotina no resgistrador GICC\textunderscore{}EOIR, que indica que a interrupção já foi servida;
\begin{lstlisting}[language=C]
void irq_dispatcher_c(void) {
  uint32_t irq_id = GICC_IAR & 0x3FF; // le o identificador da interrupcao

  // verifica se o indenficador nao e maior que o maximo de interrupcoes configuradas e se existe uma rotina de tratamento armazenada no vetor interrupt_handlers
  if (irq_id < MAX_INTERRUPTS && interrupt_handlers[irq_id] != 0) {
    interrupt_handlers[irq_id]();
  }

  GICC_EOIR = irq_id; // marca que a interrupcao ja foi servida
}
\end{lstlisting}
Na primeira linha dessa função, utiliza-se a operação bit a bit \emph{AND} com a máscara \texttt{0x3FF} (1023 em decimal). Isso é feito porque, na especificação do GIC, o ID numérico da interrupção gerada é armazenado exclusivamente nos 10 primeiros bits do registrador \texttt{GICC\textunderscore{}IAR}. A máscara limpa qualquer outro bit residual, garantindo que a variável \texttt{irq\textunderscore{}id} contenha apenas o número limpo da interrupção (como 30 ou 33).

Por fim, o tratador realiza um retorno para o contexto do processo anterior a sua chamada para que ele possa continuar com a sua execução.

Para a utilização e configuração do tratador de forma que seja possível configurar e gerenciar interrupções, a biblioteca desenvolvida possui as seguintes funções:
\begin{itemize}
    \item Registrar rotina de tratamento

\begin{lstlisting}[language=C]
int register_interrupt_handler(uint32_t irq, isr_t handler) {
  if (irq < MAX_INTERRUPTS) {
    if (interrupt_handlers[irq] == 0) {
      interrupt_handlers[irq] = handler;
      return 0;
    } else
      // se ja tiver handler registrado, retorna erro (-2)
      return -2;
  }
  return -1; // id inválido
}
\end{lstlisting}

Recebe o identificador de interrupção \emph{irq} e um ponteiro de função \emph{handler} que aponta para a rotina de tratamento da interrupção. Essa função salva o ponteiro de função no vetor \emph{interrupt\textunderscore{}handlers} no índice \emph{irq} caso o identificador recebido não ultrapasse o valor MAX\textunderscore{}INTERRUPTS. Retorna 0 caso tenha sido possível salvar o \emph{handler} senão -1.
    \item Ativar interrupção

\begin{lstlisting}[language=C]
void gic_enable_interrupt(uint32_t irq) {
  if (irq >= MAX_INTERRUPTS)
    return;

  // cada registrador tem 32 bits
  uint32_t reg_index = irq / 32;  // qual registrador
  uint32_t bit_offset = irq % 32; // qual bit do registrador

  GICD_ISENABLER[reg_index] |= (1 << bit_offset);
}
\end{lstlisting}

Recebe o identificador de interrupção \emph{irq} e habilita o registrador GICD\textunderscore{}ISENABLER correspondente caso identificador não ultrapasse o valor MAX\textunderscore{}INTERRUPTS, habilitando-o para o tratamento de interrupção adequado.
    \item Desativar interrupção

\begin{lstlisting}[language=C]
void gic_disable_interrupt(uint32_t irq) {
  if (irq >= MAX_INTERRUPTS)
    return;

  uint32_t reg_index = irq / 32;
  uint32_t bit_offset = irq % 32;

  // No ICENABLER escrever 1 desliga a interrupção
  GICD_ICENABLER[reg_index] = (1 << bit_offset);
}
\end{lstlisting}

Recebe o identificador de interrupção \emph{irq} e habilita o registrador GICD\textunderscore{}ICENABLER correspondente caso identificador não ultrapasse o valor MAX\textunderscore{}INTERRUPTS, desabilitando o tratamento de interrupção correspondente.
    \item Configurar interrupções


\begin{lstlisting}[language=C]
void gic_config_interrupt(uint32_t irq, int edge_triggered) {
  uint32_t reg_index = irq / 16;
  uint32_t shift = (irq % 16) * 2;

  GICD_ICFGR[reg_index] &= ~(0b11 << shift); // Limpa os 2 bits
  if (edge_triggered) {
    GICD_ICFGR[reg_index] |= (0b10 << shift); // Aplica a config
  }
}
\end{lstlisting}

Recebe o identificador de interrupção \emph{irq} e um sinal \emph{edge\textunderscore{}triggered} que indica se a interrupção é sensitiva à borda (valor 1) ou sensível ao nível (valor 0). A implementação dessa função (exibida abaixo) demonstra o controle refinado do \emph{hardware}, visto que o registrador \texttt{GICD\textunderscore{}ICFGR} reserva exatamente 2 bits para cada interrupção. O código divide o \emph{irq} por 16 para encontrar qual registrador de 32 bits acessar, e usa módulo e deslocamento (\emph{shift}) para aplicar a máscara (\texttt{0b11}) no par de bits correto.

\end{itemize}

\section{Testes e Verificação}
%-------------------------------------------------------------------------------

% Tópicos a cobrir:

Para o teste da funcionalidade, foi implementado o tratador para a interrupção de timer no método principal do projeto \emph{kmain()}, que tem por objetivo imprimir na tela uma mensagem de aviso que o processador sofreu uma interrupção de timer.

Para isso, na função \emph{kmain()}, é realizado a inicialização do serial do projeto por meio da função \emph{serial\textunderscore{}init()}, depois a CPU é inicializada para apontar para a tabela de vetores por meio da função \emph{setup\textunderscore{}core\textunderscore{}for\textunderscore{}irq}. Somente após configurar a controladora GIC, as interrupções da CPU, que haviam sido desligadas por segurança no \emph{boot}, são finalmente ligadas com a função \emph{enable\textunderscore{}cpu\textunderscore{}interrupts()}. Esta função abstrái a instrução \emph{inline assembly} \texttt{\_\_asm\_\_ volatile("cpsie i")}, que destranca o bit de inibição de interrupção no registrador da CPU. Por fim, é chamada a função de inicialização do timer (\emph{init\textunderscore{}timer}), que também faz uso intensivo do coprocessador de controle \texttt{p15} para ler as frequências de \emph{hardware}. Após essas configurações, um laço infinito é definido que imprime uma mensagem no console do QEMU indicando que o processo está operando normalmente no processador, com um segundo laço que serve apenas para espaçar o tempo de impressão de uma mensagem para outra, até sofrer uma interrupção de timer.
\begin{lstlisting}[language=C]
void kmain(void) {
  serial_init();
  serial_puts("Bem-vindo ao UFSKernel!\n");
  serial_puts("Executando em modo ARM bare-metal no QEMU.\n");

  serial_puts("Preparando CPU (VBAR e Pilha IRQ)...\n");
  setup_core_for_irq();

  serial_puts("Configurando GIC...\n");
  init_gic();

  serial_puts("Ligando interrupcoes...\n");
  enable_cpu_interrupts();

  serial_puts("Ativando Timer...\n");
  init_timer();

  while (1) {
    serial_puts("Kernel rodando na main...\n");
    // Um delay apenas para nao flodar a tela
    for (volatile int i = 0; i < 50000000; i++);
  }
}
\end{lstlisting}

Antes de inicializar o timer, precisamos saber a frequência base do relógio do sistema. Isso é feito consultando diretamente o coprocessador \texttt{p15} através da função \texttt{read\_cntfrq()}:

\begin{lstlisting}[language=C]
static inline uint32_t read_cntfrq(void) {
  uint32_t val;
  // Le a frequencia do clock base gravada no registrador CNTFRQ
  __asm__ volatile("mrc p15, 0, %0, c14, c0, 0" : "=r"(val));
  return val;
}
\end{lstlisting}

O inicializador do timer \emph{init\textunderscore{}timer()} lê a frequência de ciclo do hardware, divide a frequência de ciclo pelo valor SYSTEM\textunderscore{}HZ, que marca a frequência das interrupções de timer, para indicar quantos ticks ele deve aguardar antes de realizar uma interrupção, inicializa o timer com o valor de ticks calculado, registra a interrupção pela função \emph{register\textunderscore{}interrupt\textunderscore{}handler()} e habilita a interrupção pela função \emph{gic\textunderscore{}enable\textunderscore{}interruption()}.
\begin{lstlisting}[language=C]
void init_timer(void) {
  uint32_t hardware_freq = read_cntfrq();
  // quantos ticks formam um quantum no sistema
  ticks_p_q = hardware_freq / SYSTEM_HZ;

  // inicializa o timer com ticks_p_q
  __asm__ volatile("mcr p15, 0, %0, c14, c2, 0" ::"r"(ticks_p_q));
  uint32_t ctl = 1;
  __asm__ volatile("mcr p15, 0, %0, c14, c2, 1" ::"r"(ctl));

  // Toda interrupcao deve se registrar no despachante do GIC
  if (!register_interrupt_handler(TIMER_IRQ, timer_callback))
    serial_puts("Registrando timer no GIC...\n");
  else
    serial_puts("Erro ao registrar timer no GIC!\n");

  // ativando a interrupcao apos registrar
  gic_enable_interrupt(TIMER_IRQ);
}
\end{lstlisting}
Para a rotina de testes da interrupção configurada, a interrupção de timer chama a função \emph{timer\textunderscore{}callback()}, que imprime uma pequena mensagem alertando que uma interrupção de timer ocorreu, exatamente como deveria, variando apenas caso o valor de SYSTEM\textunderscore{}HZ for configurado de uma forma diferente da já definida para o processo.
\begin{lstlisting}[language=C]
// funcao que sera chamada quando a interrupcao for ativada
static void timer_callback(void) {
  serial_puts(">>> TICK DO TIMER <<<\n");

  // recarrega o timer
  __asm__ volatile("mcr p15, 0, %0, c14, c2, 0" ::"r"(ticks_p_q));

  // e aqui que o codigo fara a chamada para o
  // escalonador
}
\end{lstlisting}
